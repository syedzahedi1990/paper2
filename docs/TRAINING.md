# Training and profiling

The executable backend is `paper2.training.runner.run_training`, using pinned TRL 0.20.0 trainers and PEFT LoRA. Tiny random-model integration tests establish implementation behavior, not full-model feasibility or scientific results. The active design is the pinned Mistral 24B lineage with `natural_answer_cap_v2`, RL beta 0.04 and the 12-candidate constant/no-warmup panel. The [29 October model amendment](amendments/2026-10-29-model-and-profiling.md), [30 October completion/KL amendment](amendments/2026-10-30-natural-answer-and-kl.md) and [execution-integrity addendum](amendments/2026-10-30-execution-integrity.md) take precedence over the archived original settings.

## Fixed design and explicit implementation choices

`configs/amended_20261030/` contains the three ×1 reference pilot configurations: reasoning RL, answer-only RL and label-only SFT, clean data, seed 1. `configs/confirmatory/` contains the intended 24 runs: four arms × clean/shortcut × seeds 1, 2, 3. Both stages use `mistralai/Mistral-Small-24B-Instruct-2501`, revision `9527884be6e5616bdd54de542f9ae13384489724`, with the frozen [model amendment](MODEL_PLAN.md). Every learning arm starts independently from this original instruct checkpoint. Mutable revisions are rejected. These configurations are not selected final rates or confirmation approval. `configs/pilot/` and `configs/profile_3b.json` preserve the historical Qwen/zero-KL arrangement; do not use them for the current experiment.

All arms use LoRA on `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`. This allows both attention and MLP changes and must accompany interpretation of Test 3. The proposal fixes the modules, GRPO group size 8 and trace cap 384; rank 16, alpha 32, dropout 0 and AdamW remain declared implementation choices.

The reference learning rates are transcribed from [Zhong et al., Appendix E](https://arxiv.org/html/2606.09092v1): **2e-5 for RL and 1e-6 for SFT**. Zhong's reported LLM KL coefficient is zero. The active Paper 2 amendment instead fixes **beta 0.04 for both RL arms**, against the pinned untrained base with the adapter disabled; SFT has no KL objective. This is a chosen post-outcome setting, not a Zhong-derived LoRA optimum. RL uses per-device batch 1, rollout group 8 and gradient checkpointing. SFT uses batch 2 with accumulation 4, an effective batch of eight stories. Zhong does not specify LoRA versus full fine-tuning; its two epochs and four H100s are not replicated. Paper 2 keeps one pool pass on one device. Its [official repository](https://github.com/jkz-338/Robust-ToM-RL) contained only a README on 29 October 2026 and supplied no runnable scheduler or LoRA settings.

### Active development panel and amendment chronology

The active panel has rates `{1, 3, 10, 30} × reference rate`, **constant schedule and zero warmup**, for all three pilot arms: 12 full-exposure candidates. Temperature 0.8 and top-p 1 are declared implementation choices, not attributed to Zhong. The earlier 24-candidate design crossed the same rates with a second, 5%-warmup schedule. On 29 October, the resource decision selected the 12-candidate option before any full candidate learning. The model choice was also made on 29 October from untrained development screens. The 30 October outcome-informed amendment changes completion generation, punctuation scoring and KL, restarts the panel from the base, and retains its 12-candidate structure. It does not justify selecting a setting from the superseded panel.

The four **SFT rates are `{1e-6, 3e-6, 1e-5, 3e-5}`** and the four **RL rates are `{2e-5, 6e-5, 2e-4, 6e-4}`**. [Thinking Machines, “LoRA Without Regret”](https://thinkingmachines.ai/blog/lora/) motivates a broad panel through an empirical LoRA/full-fine-tuning rate difference; it does not establish an optimum for Mistral 24B or this task. Low SFT learning, high-rate instability and matching near step zero remain reportable outcomes.

The machine-readable [selection specification](../configs/development_selection.json) and `paper2 matrix --stage pilot --development-panel --output runs/development-panel` export the exact current 12 configurations and their hashed plan without launching training. This retains **372 evaluated adapters**: four settings × 93 snapshots across the three arms. Freeze a costed registry before candidate learning. The public historical export is explicit: `paper2 matrix --stage pilot --development-panel --design legacy_proposal --output runs/historical-development-panel`; it produces the old 24-candidate/two-schedule design for historical inspection, not current approval. The 29 October staged resource amendment is preserved as `runs/vast-20261029/operator/2026-10-29-staged-pilot-resource-amendment.md`, SHA-256 `fa5b7e0a7e549d039ba2aa34a65767000ec2e4c44f8a7b0bcb5665757f1dd8f3`; its frozen resource decision was recorded at 16:35 UTC that day, before full candidate learning. Transfer selected family settings to confirmation only after the complete amended panel and required reviews; the shipped confirmatory rates remain provisional.

For a panel, score every candidate on the same 120 development stories at its final step in the arm's native format. Choose the RL setting maximizing mean development accuracy across reasoning RL and answer RL; choose the SFT setting using label SFT. Both members of each objective family then share that setting, including reasoning SFT in confirmation. Break exact ties by the smaller learning rate, then no warmup. Retain all candidate scores and story-bootstrap intervals, failures and compute; a numerical software failure is reported for review, never replaced with a favorable run. The reviewer may stop or revise the pilot with a dated protocol amendment, but cannot inspect confirmation data to choose settings. Freeze the selected setting before the confirmatory grid. No improvement threshold is introduced. The inherited rates are not asserted to be optimal for LoRA, and these objective-specific choices do not remove optimization confounding.

The shipped learning runs use `max_steps: null` and `num_train_epochs: 1.0`. The runner resolves this in prompt-group units: with 2,000 training worlds, batch size 1, accumulation 8 and GRPO group size 8, RL needs **2,000 optimizer steps and 16,000 sampled completions** for one pool pass. SFT, with batch size 2 and accumulation 4, needs **250 optimizer steps and 2,000 supervised examples**. This aligns story exposure, not optimizer steps, tokens or compute. The manifest records the resolved budget. Explicit production budgets shorter than one pool pass are rejected outside profiling, and a completed production learning run fails if its measured unique-world IDs do not cover the full pool. No claim that G1 passed follows from merely completing this budget. Retain learning curves and matched immediate-answer comparisons alongside unconditional comparisons; the larger corrected RL budget must be included in the GPU profile and cost estimate.

GRPO uses group size 8, batch size 1 and gradient accumulation 8 on one GPU, one generation per optimization step, the GRPO loss, and group-standardized rewards. The audited generation arrangement is Transformers `generate`, standard KV caching, gradient checkpointing and bfloat16, with no vLLM or distributed trainer. A 4-bit option exists but requires a compatible `bitsandbytes` installation and a new profile. Models are not quantized by default. The checked dependency versions are torch 2.7.1, transformers 4.53.2, TRL 0.20.0, PEFT 0.16.0, accelerate 1.8.1 and datasets 3.6.0.

The active `natural_answer_cap_v2` permits at most **384 sampled tokens for the entire reasoning completion, including the natural answer delimiter and answer**. It never inserts a delimiter or makes a rescue answer call. A complete terminal `Answer: X` at token 384 is valid without EOS; an absent, malformed, incomplete or out-of-budget answer earns zero. Accept one optional adjacent terminal period, not extra prose or multiple periods. Rewards use the actual sampled IDs before GRPO advantages, and failed tokens stay in the loss. There is no minimum prose length or separate reward for trace content, length or non-repetition. Answer-only native completion remains capped at four tokens with the same optional period. Immediate next-token scoring and official OpenToM scoring are unchanged. The superseded `legacy_forced_answer_v1` inserted an answer delimiter after a prose-only cap; retain those old results under their original parser, never silently rescore or use them for current selection.

SFT uses explicit tokenized completion masks: prompt and padding tokens are excluded. Label SFT supervises the direct answer plus EOS. Reasoning SFT supervises a symbolic trace, direct answer and EOS. No language-model loss is silently applied to the story. Prompt-length overflow raises an error instead of truncating events.

## Reasoning SFT source and additional information

The trace source is `paper1_symbolic_oracle_v1`, saved in `supervision/{clean,shortcut}_reasoning_sft.jsonl`. It is a deterministic task-world rollout explaining focal initial state, observation/communication updates and the queried belief. It supplies privileged intermediate belief-state information that label SFT and outcome RL do not receive. The exact trace source, extra information and supervised token counts are recorded in manifests. It must be reported as an asymmetry, not treated as matched supervision. Oracle traces that exceed 384 tokenizer tokens are rejected so their template can be shortened before training. No unrewarded consequence answer is supervised.

## Data, gates and profiling

Only direct-view training rows may enter the trainer. Full world metadata and any trace are removed at the RL boundary. Training files, row content and corpus manifest are checked against the frozen G0 manifest. Production corpus counts must be 2,000 training worlds, 120 development and 120 confirmation worlds. Learning curves evaluate every frozen clean development direct question in the immediate-answer format and the arm's native format on separate preregistered schedules. Immediate evaluation uses the full-vocabulary greedy next token; invalid tokens are wrong. Native evaluation generates an uninterrupted greedy completion using the same trace cap and answer-correctness parser as training: reasoning arms write a trace and answer, while answer-only arms complete the answer. G1 reviews native-format learning from step zero for **all three pilot arms**, with their immediate curves and separate written interpretations; immediate accuracy remains the Test 1 transfer and checkpoint-matching measure. Confirmation data cannot serve as training evaluation.

The default RL schedule measures **immediate-answer accuracy and saves adapters at steps 0, 50, 100, …, 2,000** (41 checkpoints), while expensive native-format generation runs only at **0, 250, 500, …, 2,000** (9 panels). SFT evaluates both formats at 0, 25, 50, …, 250 (11 checkpoints). Both schedules always include the final step even when it falls between regular intervals. A step on both schedules saves its adapter once. The profile config keeps both intervals at five steps and measures the base and final model.

`eval_steps` retains its native-completion meaning; the new `immediate_eval_steps` controls cheap accuracy measurements and matching snapshots. Shipped RL configurations set them explicitly to 250 and 50; SFT uses 25 and 25. For an older config that omits the new field, the immediate interval defaults to the smaller of `eval_steps` and 50 for RL (25 for SFT), preserving short test/profile schedules. Both fields enter the frozen training configuration; resuming a run whose recorded configuration predates this change requires a fresh run rather than silently changing its schedule.

Native development generation remains sequential in the frozen runner. Each RL run has **1,080 native generations plus 4,920 immediate forward passes**. The amended reasoning bound is **384 sampled tokens per completion**, or **414,720 native development completion tokens per RL run**. This is a token-workload bound, not a time guarantee. Report per-format actual timings and counts. Denser immediate scoring improves matching resolution but adds forward-pass work and retained storage.

Matching uses all retained immediate checkpoints. Its target is the highest accuracy reached by every compared run: the minimum of their runwise maxima. Select the checkpoint closest to this common target in each run, break ties by the earlier step, and report actual accuracies and their deviations from the target. There is no tolerance cutoff and no interpolated adapter. Native accuracy and G1 evidence only update on native evaluation steps, with no copied native score at intervening immediate checkpoints. SFT and RL differ in learning rate and optimizer steps; only story exposure is matched. Matched immediate-answer accuracy is an additional comparison, not proof that optimization differences have been removed.

The profile stage requires frozen, reviewed G0 but no prior profile. Prepare separate amended 24B profile configurations for all three pilot arms, with an explicit five-update budget and full 120-story immediate/native evaluation at step zero and final. The dated amendment permits a fresh 25-update extension if needed on resource-stability grounds, decided before that extension and never from accuracy. Five-update or longer measurements are planning evidence, not full-budget guarantees. Historical `configs/profile_3b.json` and beta-zero reports cannot authorize this arrangement. Measure training, native/immediate evaluation, snapshot saves and later experiments separately; include every arm and seed. Learned trace lengths can change costs. Preserve measured lengths and full-cap sensitivity scenarios without calling them time upper bounds. Profiling adapters never initialize candidate arms.

Every full production run requires a completed real GPU profile for the same model, immutable revision, arm and model-amendment hash, with matching generation and memory choices. Profile validation follows the measured objective: RL requires actual sampled rollouts and generation throughput; SFT requires supervised/optimized tokens, prompt exposures and optimization time, while its training rollout counts remain zero and rollout throughput is undefined. Both require measured native/immediate development evaluation and adapter storage. Create a separate profile configuration for answer RL and label SFT; the reasoning-RL profile cannot substitute for them. After G0–G4 and cost approval, an initial target-model profile can run with `stage="confirmatory", profile=true, target_profile_bootstrap=true` using a profile of the calibrated pilot model as its prerequisite; this explicitly declared profiling run may change arm or memory settings. Use the completed target-model/arm report for subsequent training. A synthetic CPU report cannot unlock it. Every confirmatory model still requires G0–G4 evidence and the explicit cost approval checked by `paper2.gates`. No exception bypass is exposed through the CLI. The only ungated path requires an in-memory tiny model below one million parameters for offline tests.


### G1 trace length and actual editability

Every native reasoning checkpoint retains raw completion text and sampled IDs. Trace-health v1 remains immutable and is recomputed exactly when verifying historical receipts. The separate v2 reanalysis adds sampled completion-token counts, trace character/whitespace-word lengths, raw distributions and mean intervals using 20,000 whole-story resamples. This distinguishes a set of different one-word traces from longer explanations without a length threshold. If a token spans the trace/answer text boundary, exact sampled trace-token allocation is unavailable: report enclosing sampled-prefix bounds and any separately labelled re-tokenized proxy. Never substitute re-encoded IDs for generated IDs.

`paper2 trace-health --input RUN/checkpoint_predictions.jsonl --original-health RUN/checkpoint_trace_health.jsonl --output runs/trace-health-lengths-v2.json` writes a separate input-hash-bound report. It performs no generation and refuses to overwrite an existing output. The optional pinned tokenizer enables trace-token attribution; completion counts and text lengths need no tokenizer.

The G1 fixed-editor job uses **all 1,080 saved native direct-question traces per selected reasoning-RL run** (nine checkpoints × 120 worlds), preserving sampled IDs and source hashes. Freeze its editor/provenance and contract manifest before classification. Do not regenerate traces, substitute a favorable checkpoint or infer editability from accuracy, repetition or wording. Keep unassessed, missing-belief, contradicted and failed classifications in reported denominators. The available `paper2 g1-editability` prepare/generate/finalize/resources workflow separates preparation, model work and resource reporting. Model classifications do not count as human review: G3 still needs the preregistered random sample completed by a named human. See the [execution-integrity addendum](amendments/2026-10-30-execution-integrity.md) for the bound workflow.

## Outputs and compute accounting

Each run writes `run_manifest.json`, `learning_curve.jsonl`, `compute_report.json`, resumable `checkpoint-*` directories, and a final LoRA adapter/tokenizer under `adapter/`. Profiling also writes `profile_report.json`. Every evaluated step preserves its adapter/tokenizer in `evaluated_checkpoints/checkpoint-{step}/`; resumable rotation does not remove these matching snapshots. The three-arm single-setting pilot retains **93** evaluated adapters, the active 12-candidate panel **372**, and the intended 24-run confirmatory grid **624**. Final adapters and optimizer checkpoints are additional. The amended candidate retention is `save_total_limit=2`, including space for a temporary third resumable checkpoint during rotation. Use actual bytes and the frozen lifecycle policy; no deletion of old evidence is implied.

`checkpoint_evaluations.jsonl` contains one summary per checkpoint and format with `path`, `checkpoint_id`, adapter hash, `arm`, training `dataset`, evaluation dataset, `seed`, `split`, `view`, `format`, `accuracy` and `step`. It is the direct input to `paper2 analyze match`; matching uses only immediate/direct/development entries and keeps dataset/seed identities. `checkpoint_predictions.jsonl` retains every world-level result for paired analyses and aggregation of seeds within story. `g1_learning_evidence.json` links the base and latest native-format scores and records their difference. On run completion, schema 3 binds the completed manifest, compute report, checkpoint summaries and world-level predictions by hash. G1 must list all three completed clean seed-1 runs of the calibrated pilot model (Mistral 24B in the active lineage), each with a written interpretation, via `gates.G1.learning_curves`; each receipt must also appear in G1’s ordinary hashed evidence list. The checker verifies shared development worlds and complete scheduled native/immediate curves, including step zero and the final step. Missing curves or tampering are integrity failures; a flat or negative curve is valid evidence for the reviewer, not an automatic pass or failure. If the development panel was used, retain every candidate curve/score and document the chosen setting; never hide failed candidates. This is evidence for review, not an automatic G1 pass. Resuming upserts repeated checkpoint/format observations rather than duplicating them.

`run_manifest.json.resource_plan` records separate `evaluation_native_steps` and `evaluation_immediate_steps`, their panel counts, and their union in `evaluation_steps`/`evaluation_panels`. It also records native generation count and batch size, immediate forward calls, tokenizer-specific completion cap, completion-token upper bound, evaluated adapters and rotating checkpoint counts. `compute_report.json` records actual per-format panel counts and seconds, their combined `evaluation_seconds`, native generated tokens, separate evaluated/resumable/final save times and the maximum measured evaluated-adapter directory size. Its `evaluation_panels` counts evaluation events with either or both formats, rather than double-counting a shared step. Repeated evaluations after resume count as actual compute.

`profile_report.json.full_pool_resource_projection` projects a one-pool run of the **same arm and model**, using the shipped 250-step native/50-step immediate RL schedule, 25-step SFT schedule and 50-step resumable-save schedule. Its explicit `target_config` must match the intended run before using it. Training and orchestration time are scaled by optimizer steps; native and immediate development times are scaled independently by their respective panel counts; saves are scaled by their own counts. This avoids multiplying the two profile evaluations by the training-step ratio. The report leaves the total unset if any required timing is missing, including older profiles that contain only a combined evaluation duration. Evaluated-adapter storage is projected from measured snapshot bytes; optimizer checkpoint, final adapter, base-model and dataset storage remain separate. The estimate is a planning aid requiring resource review and the declared extension when needed, not a gate pass or a budget guarantee. Model loading precedes the measured training timer, and later Tests 1–3 add compute.

The ledger records input training examples, actual distinct world IDs seen, realized pool coverage and answer supervision; prompt exposures (one story per RL group or SFT forward pass); sampled completions; prompt instances including group repetition; generated and optimized tokens; supervised and forced-format tokens; cap hits and truncation; generation, generation-plus-scoring, forward/backward-plus-optimizer, evaluation and checkpoint durations; peak CUDA allocation; occupied GPU seconds; and learning curves. Timing synchronizes CUDA. `update_seconds` includes forward/backward and optimizer time but not inter-step orchestration or gradient-clipping overhead, so use occupied GPU wall time for costs. Truncation means absence of EOS within the generation budget; it differs from reaching the trace cap. No GPU time is invented for CPU tests.

The underlying runner supports resumption only from a checkpoint in the original output directory with the original config and training digest. This compatibility mechanism does not authorize retry/resumption in the current frozen supervised candidate panel; preserve interrupted attempts and follow its execution decision. Each checkpoint includes its ledger snapshot, so completion/token counters resume at that checkpoint rather than restarting at zero. `learning_curve.jsonl` is append-only; step numbers identify repeated observations after a resume.

## Upstream API references

The backend follows the versioned [TRL GRPO API](https://huggingface.co/docs/trl/v0.20.0/en/grpo_trainer) and [TRL SFT API](https://huggingface.co/docs/trl/v0.20.0/en/sft_trainer). Instrumentation relies on version-specific hooks, so the runner rejects unvalidated package versions rather than silently changing the estimator or accounting.
