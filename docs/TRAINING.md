# Training and profiling

The executable backend is `paper2.training.runner.run_training`. It uses TRL 0.20.0 SFTTrainer and GRPOTrainer with PEFT LoRA. The integration tests train a randomly initialized tiny Qwen model locally; they never download model weights. They test all four arms, saved adapters, a nonzero RL parameter update, supervision masks, correctness rewards and the trace cap. These tests establish implementation behavior, not 3B/7B feasibility or scientific results.

## Fixed design and explicit implementation choices

`configs/pilot/` contains exactly reasoning RL, answer-only RL and label-only SFT, clean data, seed 1, Qwen2.5-3B-Instruct. `configs/confirmatory/` contains 24 runs: four arms × clean/shortcut × seeds 1, 2, 3, Qwen2.5-7B-Instruct. Every arm starts from the same original instruct checkpoint; the shipped configs pin immutable base revisions, with the same revision used across each comparison. The official model metadata resolves [3B](https://huggingface.co/api/models/Qwen/Qwen2.5-3B-Instruct) to `aa8e72537993ba99e69dfaafa59ed015b17504d1` and [7B](https://huggingface.co/api/models/Qwen/Qwen2.5-7B-Instruct) to `a09a35458c702b33eeacc393d103063234e8bc28`. Mutable branch names are rejected for production training. Resolved model commit hashes are recorded in run manifests.

All arms use LoRA on `q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`. This allows both attention and MLP changes and must accompany interpretation of Test 3. The proposal fixes the modules, GRPO group size 8 and trace cap 384; rank 16, alpha 32, dropout 0 and AdamW remain declared implementation choices.

The reference learning rates are transcribed from [Zhong et al., Appendix E](https://arxiv.org/html/2606.09092v1): **2e-5 for RL and 1e-6 for SFT**. The LLM KL coefficient is **0**, correcting the former 0.04 (their VLM setting). RL uses their per-device batch 1, rollout group 8 and gradient checkpointing. SFT uses their per-device batch 2 with accumulation 4 here, keeping the effective single-GPU batch at eight stories. Their paper does not specify LoRA versus full fine-tuning, so these rates are reference candidates, not validated settings for our rank-16 adapters. Their experiments used two epochs and four H100s; Paper 2 retains one pool pass on one device to preserve its approved exposure design and compute planning. This is an explicit departure, not an exact training replication. Their [official repository](https://github.com/jkz-338/Robust-ToM-RL) contained only a README on 29 October 2026; it did not supply a scheduler, LoRA configuration or runnable training settings.

### Development selection rule, fixed before pilot learning

Keep the reported rates as the ×1 reference candidates; do not assume that they provide comparable optimization of the LoRA arms. The constant-with-5%-warmup schedule, temperature 0.8 and top-p 1 are declared pilot choices, not settings attributed to Zhong. Before launching any learning comparison, the G0 reviewer records either the inherited configuration alone or a costed development-selection panel in the frozen calibration. The optional panel consists of rates `{1, 3, 10, 30} × reference rate` crossed with schedules `{constant/no warmup, constant_with_warmup/0.05}`; all other settings and one-pass story exposure are identical. It is fixed as a whole before seeing learning results; no adaptive additions after a poor outcome.

This gives **SFT rates `{1e-6, 3e-6, 1e-5, 3e-5}`** and **RL rates `{2e-5, 6e-5, 2e-4, 6e-4}`**, each with both schedules. [Thinking Machines, “LoRA Without Regret”](https://thinkingmachines.ai/blog/lora/) found an approximately tenfold LoRA/full-fine-tuning rate difference in its experiments. That empirical finding motivates a broad search; it does not establish the optimum for this task, Qwen2.5 or our one-pass budget. Low SFT learning, high-rate instability and a matching target near step zero are all possibilities to report and review.

The machine-readable [selection specification](../configs/development_selection.json) and `paper2 matrix --stage pilot --development-panel --output runs/development-panel` export the 24 candidate configurations and a hashed plan without launching training. This is eight settings for each of three pilot arms, **eight times** the one-setting pilot's run count and **744 evaluated adapters** instead of 93; cost training, evaluation and adapter storage for all candidates before choosing this option. The ordinary pilot JSON files remain ×1 reference configurations, not selected final hyperparameters. If a one-setting pilot is chosen for budget reasons, record that decision before learning and explicitly review its optimization limitations at G1; do not call its reference rates LoRA-validated. Transfer the selected family rate/schedule to the confirmatory configurations and freeze them before the paid grid; the shipped final JSON files are also provisional references.

For a panel, score every candidate on the same 120 development stories at its final step in the arm's native format. Choose the RL setting maximizing mean development accuracy across reasoning RL and answer RL; choose the SFT setting using label SFT. Both members of each objective family then share that setting, including reasoning SFT in confirmation. Break exact ties by the smaller learning rate, then no warmup. Retain all candidate scores and story-bootstrap intervals, failures and compute; a numerical software failure is reported for review, never replaced with a favorable run. The reviewer may stop or revise the pilot with a dated protocol amendment, but cannot inspect confirmation data to choose settings. Freeze the selected setting before the confirmatory grid. No improvement threshold is introduced. The inherited rates are not asserted to be optimal for LoRA, and these objective-specific choices do not remove optimization confounding.

The shipped learning runs use `max_steps: null` and `num_train_epochs: 1.0`. The runner resolves this in prompt-group units: with 2,000 training worlds, batch size 1, accumulation 8 and GRPO group size 8, RL needs **2,000 optimizer steps and 16,000 sampled completions** for one pool pass. SFT, with batch size 2 and accumulation 4, needs **250 optimizer steps and 2,000 supervised examples**. This aligns story exposure, not optimizer steps, tokens or compute. The manifest records the resolved budget. Explicit production budgets shorter than one pool pass are rejected outside profiling, and a completed production learning run fails if its measured unique-world IDs do not cover the full pool. No claim that G1 passed follows from merely completing this budget. Retain learning curves and matched immediate-answer comparisons alongside unconditional comparisons; the larger corrected RL budget must be included in the GPU profile and cost estimate.

GRPO uses group size 8, batch size 1 and gradient accumulation 8 on one GPU, one generation per optimization step, the GRPO loss, and group-standardized rewards. The audited generation arrangement is Transformers `generate`, standard KV caching, gradient checkpointing and bfloat16, with no vLLM or distributed trainer. A 4-bit option exists but requires a compatible `bitsandbytes` installation and a new profile. Models are not quantized by default. The checked dependency versions are torch 2.7.1, transformers 4.53.2, TRL 0.20.0, PEFT 0.16.0, accelerate 1.8.1 and datasets 3.6.0.

Reasoning traces are capped at 384 generated tokens. A trace that naturally emits `\nAnswer:` earlier ends its trace at that delimiter. At the cap, a logits processor inserts the shared `\nAnswer:` delimiter, followed by up to four normally sampled answer/EOS tokens. Injected delimiter tokens are excluded from the RL loss but remain in the attention context. Cap hits and forced token counts are reported. The cap is a generation constraint; there is no reward for trace length, trace content, agreement with an oracle, or formatting. A correct parseable direct answer receives 1, every other completion 0. Answer-only RL generates at most four tokens after `Answer:`; extra prose receives zero. Generated short traces are retained as outcomes.

SFT uses explicit tokenized completion masks: prompt and padding tokens are excluded. Label SFT supervises the direct answer plus EOS. Reasoning SFT supervises a symbolic trace, direct answer and EOS. No language-model loss is silently applied to the story. Prompt-length overflow raises an error instead of truncating events.

## Reasoning SFT source and additional information

The trace source is `paper1_symbolic_oracle_v1`, saved in `supervision/{clean,shortcut}_reasoning_sft.jsonl`. It is a deterministic task-world rollout explaining focal initial state, observation/communication updates and the queried belief. It supplies privileged intermediate belief-state information that label SFT and outcome RL do not receive. The exact trace source, extra information and supervised token counts are recorded in manifests. It must be reported as an asymmetry, not treated as matched supervision. Oracle traces that exceed 384 tokenizer tokens are rejected so their template can be shortened before training. No unrewarded consequence answer is supervised.

## Data, gates and profiling

Only direct-view training rows may enter the trainer. Full world metadata and any trace are removed at the RL boundary. Training files, row content and corpus manifest are checked against the frozen G0 manifest. Production corpus counts must be 2,000 training worlds, 120 development and 120 confirmation worlds. Learning curves evaluate every frozen clean development direct question in the immediate-answer format and the arm's native format on separate preregistered schedules. Immediate evaluation uses the full-vocabulary greedy next token; invalid tokens are wrong. Native evaluation generates an uninterrupted greedy completion using the same trace cap and answer-correctness parser as training: reasoning arms write a trace and answer, while answer-only arms complete the answer. G1 reviews native-format learning from step zero for **all three pilot arms**, with their immediate curves and separate written interpretations; immediate accuracy remains the Test 1 transfer and checkpoint-matching measure. Confirmation data cannot serve as training evaluation.

The default RL schedule measures **immediate-answer accuracy and saves adapters at steps 0, 50, 100, …, 2,000** (41 checkpoints), while expensive native-format generation runs only at **0, 250, 500, …, 2,000** (9 panels). SFT evaluates both formats at 0, 25, 50, …, 250 (11 checkpoints). Both schedules always include the final step even when it falls between regular intervals. A step on both schedules saves its adapter once. The profile config keeps both intervals at five steps and measures the base and final model.

`eval_steps` retains its native-completion meaning; the new `immediate_eval_steps` controls cheap accuracy measurements and matching snapshots. Shipped RL configurations set them explicitly to 250 and 50; SFT uses 25 and 25. For an older config that omits the new field, the immediate interval defaults to the smaller of `eval_steps` and 50 for RL (25 for SFT), preserving short test/profile schedules. Both fields enter the frozen training configuration; resuming a run whose recorded configuration predates this change requires a fresh run rather than silently changing its schedule.

Native development generation remains sequential. For 120 development worlds, an RL run now makes **1,080 native generations plus 4,920 immediate forward passes**. At a three-token answer delimiter, the reasoning completion upper bound is 391 tokens per generation, or 422,280 development completion tokens per RL run. Actual delimiter lengths, per-format times and counts are recorded from the tokenizer and runtime. Denser immediate scoring restores matching resolution without adding native traces, but it increases both forward-pass work and retained adapter storage; neither cost is free.

Matching uses all retained immediate checkpoints. Its target is the highest accuracy reached by every compared run: the minimum of their runwise maxima. Select the checkpoint closest to this common target in each run, break ties by the earlier step, and report actual accuracies and their deviations from the target. There is no tolerance cutoff and no interpolated adapter. Native accuracy and G1 evidence only update on native evaluation steps, with no copied native score at intervening immediate checkpoints. SFT and RL differ in learning rate and optimizer steps; only story exposure is matched. Matched immediate-answer accuracy is an additional comparison, not proof that optimization differences have been removed.

The profile stage requires frozen, reviewed G0 but does not require a prior profile. `configs/profile_3b.json` starts with five representative GRPO updates and a checkpoint. Extend its length on the target GPU to measure steady-state speed and variance before accepting a compute estimate; five steps are an initial smoke profile, not evidence for the full budget. The proposal's 15–25 GPU-hour budget for the whole 3B pilot is **not established** by this implementation. Measure training, native development evaluation, snapshot saves and the later experiments, and include every arm and seed in the cost review. A reasoning-RL profile cannot establish the speed of the SFT or answer-only arms. Greedy evaluation traces can become longer after learning, so profile representative lengths and report the token-cap upper bound as well as observed timings. Profiling itself changes a disposable adapter; subsequent arm runs load the original base, not that adapter.

Every full production run requires a completed real GPU profile for the same arm, with matching generation and memory choices. Profile validation follows the measured objective: RL requires actual sampled rollouts and generation throughput; SFT requires supervised/optimized tokens, prompt exposures and optimization time, while its training rollout counts remain zero and rollout throughput is undefined. Both require measured native/immediate development evaluation and adapter storage. Create a separate profile configuration for answer RL and label SFT; the reasoning-RL profile cannot substitute for them. After G0–G4 and cost approval, a target-size 7B profile can run with `stage="confirmatory", profile=true` using the prior 3B profile as its prerequisite; this new profiling run may change memory settings. Use its completed report for subsequent 7B training. A synthetic CPU report cannot unlock it. Confirmatory 7B training additionally requires G0–G4 evidence and the explicit cost approval checked by `paper2.gates`. No exception bypass is exposed through the CLI. The only ungated path requires an in-memory tiny model below one million parameters for offline tests.

## Outputs and compute accounting

Each run writes `run_manifest.json`, `learning_curve.jsonl`, `compute_report.json`, resumable `checkpoint-*` directories, and its final LoRA adapter/tokenizer under `adapter/`. Profiling additionally writes `profile_report.json` with status `completed`. Every step evaluated in either format, including the base at step zero and the final step, preserves a lightweight adapter plus tokenizer in `evaluated_checkpoints/checkpoint-{step}/`. These snapshots are not removed by the rotation of resumable trainer checkpoints. Evaluation and checkpoint intervals may therefore differ without leaving a selectable step with missing weights. The default pilot retains **93 evaluated adapters** in total (two RL runs × 41, one SFT run × 11); the confirmatory grid retains **624** (12 RL runs × 41, 12 SFT runs × 11). This is 32 additional snapshots per RL run compared with the former shared 250-step evaluation cadence. Storage also includes the separate final adapter and up to six rotating resumable checkpoints per run; resumable checkpoints contain optimizer state. Use measured bytes, not a fixed model-size estimate, when reserving disk.

`checkpoint_evaluations.jsonl` contains one summary per checkpoint and format with `path`, `checkpoint_id`, adapter hash, `arm`, training `dataset`, evaluation dataset, `seed`, `split`, `view`, `format`, `accuracy` and `step`. It is the direct input to `paper2 analyze match`; matching uses only immediate/direct/development entries and keeps dataset/seed identities. `checkpoint_predictions.jsonl` retains every world-level result for paired analyses and aggregation of seeds within story. `g1_learning_evidence.json` links the base and latest native-format scores and records their difference. On run completion, schema 3 binds the completed manifest, compute report, checkpoint summaries and world-level predictions by hash. G1 must list all three completed clean 3B/seed-1 pilot runs, each with a written interpretation, via `gates.G1.learning_curves`; each receipt must also appear in G1’s ordinary hashed evidence list. The checker verifies shared development worlds and complete scheduled native/immediate curves, including step zero and the final step. Missing curves or tampering are integrity failures; a flat or negative curve is valid evidence for the reviewer, not an automatic pass or failure. If the development panel was used, retain every candidate curve/score and document the chosen setting; never hide failed candidates. This is evidence for review, not an automatic G1 pass. Resuming upserts repeated checkpoint/format observations rather than duplicating them.

`run_manifest.json.resource_plan` schema 2 records separate `evaluation_native_steps` and `evaluation_immediate_steps`, their panel counts, and their union in `evaluation_steps`/`evaluation_panels`. It also records native generation count and batch size, immediate forward calls, tokenizer-specific completion cap, completion-token upper bound, evaluated adapters and rotating checkpoint counts. `compute_report.json` records actual per-format panel counts and seconds, their combined `evaluation_seconds`, native generated tokens, separate evaluated/resumable/final save times and the maximum measured evaluated-adapter directory size. Its `evaluation_panels` counts evaluation events with either or both formats, rather than double-counting a shared step. Repeated evaluations after resume count as actual compute.

`profile_report.json.full_pool_resource_projection` projects a one-pool run of the **same arm and model**, using the shipped 250-step native/50-step immediate RL schedule, 25-step SFT schedule and 50-step resumable-save schedule. Its explicit `target_config` must match the intended run before using it. Training and orchestration time are scaled by optimizer steps; native and immediate development times are scaled independently by their respective panel counts; saves are scaled by their own counts. This avoids multiplying the two profile evaluations by the training-step ratio. The report leaves the total unset if any required timing is missing, including older profiles that contain only a combined evaluation duration. Evaluated-adapter storage is projected from measured snapshot bytes; optimizer checkpoint, final adapter, base-model and dataset storage remain separate. The estimate is a planning aid requiring a longer GPU profile and review, not a gate pass or a budget guarantee. Model loading precedes the measured training timer, and later Tests 1–3 add compute.

The ledger records input training examples, actual distinct world IDs seen, realized pool coverage and answer supervision; prompt exposures (one story per RL group or SFT forward pass); sampled completions; prompt instances including group repetition; generated and optimized tokens; supervised and forced-format tokens; cap hits and truncation; generation, generation-plus-scoring, forward/backward-plus-optimizer, evaluation and checkpoint durations; peak CUDA allocation; occupied GPU seconds; and learning curves. Timing synchronizes CUDA. `update_seconds` includes forward/backward and optimizer time but not inter-step orchestration or gradient-clipping overhead, so use occupied GPU wall time for costs. Truncation means absence of EOS within the generation budget; it differs from reaching the trace cap. No GPU time is invented for CPU tests.

Resume only from a checkpoint in the original output directory with the original config and training digest. Each checkpoint includes its ledger snapshot, so completion/token counters resume at that checkpoint rather than restarting at zero. `learning_curve.jsonl` is append-only; step numbers identify repeated observations after a resume.

## Upstream API references

The backend follows the versioned [TRL GRPO API](https://huggingface.co/docs/trl/v0.20.0/en/grpo_trainer) and [TRL SFT API](https://huggingface.co/docs/trl/v0.20.0/en/sft_trainer). Instrumentation relies on version-specific hooks, so the runner rejects unvalidated package versions rather than silently changing the estimator or accounting.
